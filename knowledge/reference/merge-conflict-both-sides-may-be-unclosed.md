# マージ衝突の「両方残す」は、両側が構文的に閉じているときだけ正しい

**確認日**: 2026-09-07（investing の枝取り込み・Session 20260907-998）

## 事実

**衝突ブロックの直後にある閉じ括弧は1つしかない。** 両側がどちらも関数（ブロック）の
**途中で切れている**とき、`<<<<<<<` と `>>>>>>>` を消して両方を並べると、**片方が開いたまま通る**。

```
<<<<<<< main
function A() {
  ...            ← A は閉じていない
=======
function B() {
  ...            ← B も閉じていない
>>>>>>> branch
}                ← この 1 個は A か B の片方しか閉じない
```

- git は**共通の後続行**（上の例の `}`）を衝突の外に置く。両側はそこへ合流する前提の**前半**であって、
  それぞれが完結した塊とは限らない
- 「両側が同じ場所に別のものを足しただけ」に**見える**衝突ほど危ない。
  意味の衝突はゼロなので「両方残す」で正しいのだが、**構文としては1つ足りない**

## いつ起きるか

**両側が同じ関数の末尾に別の処理を足し、その後ろに次の関数を書いたとき**。
片方の最後の文と、もう片方の先頭の関数定義が、同じ衝突ブロックに入る。
JS・Python 以外の波括弧言語でも同じ（Python はインデントなので代わりに**インデントが繋がる**形で壊れる）。

## どう防ぐか

**解決したらパーサに通す。目視では見つからない**（1,800 行のファイルで括弧を数えることになる）。

- JS: `node --check <file>`。HTML 埋め込みなら `<script>` を抜き出してから
- Python: `python3 -m py_compile <file>`
- 通らなければ、**両側のどちらが閉じていないか**を見て、足りない閉じ括弧を境目に入れる

⚠️ **エラーは「ファイルの末尾」を指す**（`Unexpected end of input`）ので、**原因の場所は教えてくれない**。
衝突を解決した箇所を疑うのが早い。

## 実例

investing で7日放置されたクラウド発の枝を取り込んだとき（`dashboard/template.html`・1,854 行）。

- 衝突2ハンクとも「両側が同じ場所に別の関数群を足した」形で、**意味の衝突はゼロ**だった
- 2つ目は HEAD 側が `renderBtc()` の**途中**、枝側が `renderFlow()` の**途中**で切れていた。
  両方残すと `renderBtc` が開いたまま
- `node --check` が `SyntaxError: Unexpected end of input` で拾った。**マージ前の両側はどちらも構文 OK**
  だったので、「マージで壊れた」と切り分けられた（両側を単体で `--check` して確かめた）
