## なぜこのノートがあるか

「メンバーだけが使えるページ」を作るとき、素朴な構成は**ページ全体を認証の後ろに置く**ことになる。
Cloudflare Access のようなエッジの認証をそのパスに立てれば、コードを書かずに守れる。

ところがこの構成には、運用で効いてくる欠点が2つある。

| 欠点 | 何が起きるか |
|---|---|
| **権限のない人に出せる画面が無い** | 認証側の既製の画面（ログイン・拒否）しか出ない。「投稿したい方は父にメールアドレスを送ってください」のような、こちらの言葉での案内が置けない |
| **認証が外れたことに気づけない** | ダッシュボードの設定が消えたり、パスが変わったりしても、ページ側は何も知らない。守られているつもりで開いている |

gonin では、最初にページ全体を Access の後ろに置き（#15）、次に「権限のない人に案内を出したい」
という要望で構成を変えた（#28）。変えた先の形がこのノート。

---

## 形

```
/post          … 誰でも届く。関数が「認証の証明」を自分で検証して振り分ける
                 証明あり → 本体（フォーム）
                 証明なし → こちらの言葉での案内 ＋「ログインして投稿する」
                 設定なし → 閉じる（fail closed）
/post/login    … ここだけを認証の後ろに置く。通ったら /post へ戻すだけ
POST /post     … 証明が無ければ 401。案内ページを出す道と、書き込む道は別
```

要点は3つ。

1. **認証の後ろに置くのは「入口」1つだけ**。入口は何もしない（戻すだけ）。認証が発行した証明
   （cookie の JWT）は、ドメイン全体で読める
2. **本体は証明を自分で検証する**。署名・発行者・宛先・期限。検証に要る設定が無ければ**閉じる**。
   これで「認証が外れても開かない」が成り立つ（不変条件・CN-013）
3. **読む道と書く道を分ける**。証明が無い人に案内を出すのは GET だけ。POST は証明が無ければ
   一律に断る。案内を出すために投稿口を緩めることにならない

## 得られるもの

- 権限のない人に、**こちらの言葉**で案内が出せる（誰に何を送れば入れるか）
- 認証の設定変更（パス・ポリシー）とコードの配信を**別々に**進められる。順番が逆でも壊れない
  ＝案内が出ないだけ（CN-018 の「重ねる」と同じ性質）
- 認証の設定が消えても本体は閉じる。守られているつもりで開く事故が無い

## 代償

- 証明の検証コードを自分で持つ（公開鍵の取得・キャッシュ・期限）。既製の認証に全部任せる
  構成より、コードが1ファイル増える
- 認証側の画面（ログイン後の拒否）は依然として既製のまま。案内が出せるのは**その手前**まで

## いつ使うか

- 「入れない人」に何かを伝えたいとき（招待の受付・問い合わせ先）
- 認証がダッシュボード設定に依存していて、外れたことを機械的に検知できないとき
- 認証の設定変更と配信を別の人・別の場所で行うとき
