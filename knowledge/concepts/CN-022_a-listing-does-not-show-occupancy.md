## なぜこのノートがあるか

CN-012 は「**未マージ≠未回収**」＝並行エージェント環境で**中身**を照合するときの話だった。
本ノートはその隣にある別の誤りを扱う。**中身が回収済みだと正しく判定できていても、
その入れ物（作業ツリー）を外してよいとは限らない。**

実測: 棚卸しで「09-10 で止まった別セッションのもの」と判定した作業ツリーを `git worktree remove` したら、
**その数分のあいだに、まったく別の新しいセッションが同じ場所に入っていた**。
枝も `claude/nishi2-…` から `claude/artifact-…` に替わっていたのに、
判断の根拠にしていたのは**数分前に取った一覧**だった。

---

## 1. 一覧が写すもの / 写さないもの

| 道具 | 写るもの | **写らないもの** |
|---|---|---|
| `git worktree list` | その場所が worktree として登録されていること・枝名・HEAD | **いま人（プロセス）が入っているか** |
| `git status` / `rev-list --count` | その瞬間の中身 | 同上 |
| セッション一覧（`list_sessions`） | `isRunning`・`cwd`・最終活動時刻 | **取得した瞬間より後のこと** |

**帰結**: **一覧はどれも「撮った時点の写真」で、占有の現在は写らない。**
中身の安全（未コミット0・未到達0）をいくら確かめても、**席が空いているかは別の問いである**。

⚠️ **時間差そのものが原因ではない**＝1秒前の一覧でも同じ穴は開く。
穴は「**一覧を撮ってから、それを根拠に壊す**」という順序にある。

---

## 2. 見落としの構造 — 変化の徴候は出ていた

今回、**枝名は実際に替わっていた**（`git worktree list` にそう出ていた）。
それでも気づけなかったのは、**外す直前に読んだ一覧を、数分前に読んだ一覧の確認として扱った**から。
記憶と食い違う欄があっても、「自分の棚卸しの前提」のほうを信じてしまう。

> **一致を確かめるつもりで一覧を読むと、食い違いが目に入らない。**
> だから**食い違い側を主語にして読む**＝「枝名は前と同じか？ 違うなら誰が替えたのか？」

---

## 3. 運用への落とし込み

1. **壊す1コマンド前に、占有を別の口で測る**（gonin では `list_sessions` の `isRunning` と `cwd`）。
   中身の安全確認（未コミット・未到達）と**同じコマンド列の中**に置く＝別の回に分けない
2. **一覧の欄が記憶と違っていたら、それ自体を「誰かが入った」の合図として扱う**（枝名・HEAD・更新時刻）
3. **壊れたら、謝る前に戻す**＝同じ場所・同じ枝で作り直す（`git worktree add <同じ path> <同じ枝>`）。
   **戻してから相手へ知らせる**。今回はコミット済みが全部戻り、相手の被害は「読み取りが1回失敗した」だけで済んだ
4. **「情報を失わないから安全」を、着手の根拠にしない**。今回の判定（全部 ahead=0・未コミット0）は
   **中身については正しかった**。外してよいかは、そこからは出てこない

## 4. なぜ CN-012 と分けるか

同じ「並行エージェント環境」から出るが、**問いが違う**。

| | CN-012 | CN-022（本ノート） |
|---|---|---|
| 問い | この成果は**本流にあるか** | この場所に**いま人がいるか** |
| 測るもの | 中身（grep・全数照合） | 占有（別系統の一覧） |
| 間違えた時 | 消してはいけない成果を消す | **他人の作業を止める** |
| 保険 | SHA 台帳・reflog | **すぐ作り直して知らせる** |

⚠️ **CN-012 の手順を丁寧にやるほど、CN-022 の穴は見えにくくなる**
＝中身の照合に時間をかけるほど、一覧を撮ってから壊すまでの間隔が開く。
