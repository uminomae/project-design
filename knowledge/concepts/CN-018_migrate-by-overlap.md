**出典**: gonin の画像置き場を git から Cloudflare R2 へ移した作業（2026-09-02）。

---

## なぜこのノートがあるか

置き場を移す作業は、素朴に書くと**「切り替え」**になる。旧を読んでいたコードを、新を読むコードに
差し替える。これは一見いちばん短い道だが、**切り替えの瞬間に落ちる窓ができる**。

gonin で画像置き場を git（`public/img/`）から R2 へ移したとき、移行に必要な変更は3つあった。

| # | 変更 | 誰が・どこで |
|---|------|------|
| 1 | 配信コードを R2 から読むようにする | セッション・repo |
| 2 | R2 のバケットを作り、Pages に繋ぐ | 本人・Cloudflare の画面 |
| 3 | 画像の実体を R2 へ移す | セッション・鍵が要る |

**この3つは同時に着かない。** 担当も置き場も違うので、必ずどれかが先に着く。素朴な切り替えは
「3つが揃った瞬間」だけが正しく、それ以外の全部の順序で壊れる。しかも今回、1 だけが先に着いた
場合に**気づきにくい形で壊れる**構造があった（後述）。

---

## 1. 「重ねる」に置き換える

切り替えではなく、**新旧を同時に生かして、優先順位だけを決める**。

```
新を見る → あれば返す
        → 無ければ旧へ落とす
```

こうすると、3つの変更がどの順序で着いても表示は途切れない。

- 1 だけ着いた（コードはあるが R2 は空）→ 旧から出る
- 1+2 が着いた（繋がったが実体が無い）→ 旧から出る
- 3 まで着いた → 新から出る
- 旧を消す → 新だけが残る＝移行完了

**移行の完了は「旧を消したとき」であって、「新を書いたとき」ではない。** 重ねる書き方は、
この2つの時点を分けられる。切り替えは分けられない。

---

## 2. 外から見える名前を変えない

重ねるための前提は、**外から見える名前（URL・キー・ID）が新旧で同じ**であること。gonin では
ページからの参照を最初から `/img/ファイル名` に固定してあり、git 期は静的ファイル、R2 期は
Functions がその URL を担う。**移行しても HTML の書き換えはゼロだった。**

名前が新旧で違うと、重ねるには「どちらの名前で来たか」を場合分けすることになり、
場合分けは移行が終わっても消えずに残る。**名前を先に固定しておくことが、あとで重ねられる条件。**

---

## 3. 素朴に書くと壊れる場所（この事例の具体）

Cloudflare Pages では、**Functions のルートが静的アセットより優先される**。
`functions/img/[[path]].js` を置いた瞬間、`/img/…` へのリクエストは静的ファイルに届かなくなる。

つまり **1 だけを配った時点で、R2 がまだ空でも、旧い静的ファイルが返らなくなる**。
素朴に「R2 に無ければ 404」と書いていたら、繋ぎ込みが済むまで画像が消えていた。

落とし先を明示することで塞いだ:

```js
// R2 に無い／まだ繋いでいない＝git に置いたままの画像を返す
return env.ASSETS.fetch(request);
```

一般化すると、**新しい層は「読む場所」を増やすだけでなく「旧い層への経路を奪う」ことがある**。
重ねるときは、奪った経路を自分で繋ぎ直す責任が生まれる。

---

## 4. どちらから出ているかを、外から見分けられるようにする

重ねた状態は、**見た目が同じまま中身だけが入れ替わる**。だから素朴に作ると、移行が進んだのか
どうかを確認できない。gonin では偶然ではなく結果的に、応答ヘッダで見分けがついた。

| 出どころ | `cache-control` |
|---|---|
| R2（Functions が付ける） | `public, max-age=3600` |
| 静的フォールバック | `public, max-age=0, must-revalidate` |

これがあったから、「バケットを繋いだ」「画像を上げた」「git から消した」の各段階で、
**実際にどちらから出ているかを毎回確かめられた**。中身の同一性も、ローカルの md5 と R2 の
etag の一致で確認した。

CN-013 の「不変条件で書く」と同じ形。**重ねた状態には、どちらが答えたかを表す観測点を
必ず1つ持たせる。** 見分けがつかない並走は、終わったかどうかを言えない。

---

## 5. 判定テスト

置き場・配信元・保存先を移す作業に当たったら、次を順に問う。

1. **外から見える名前は、新旧で同じにできるか**（できないなら、まず名前を固定する作業を先に切る）
2. **新しい層は、旧い層への経路を奪うか**（奪うなら、落とし先を自分で書く）
3. **どちらが答えたかを、外から1つの値で見分けられるか**（無いなら1つ足す）
4. **旧を消す操作は、独立した1コミットにできるか**（できるなら重なっている。できないなら切り替えになっている）

4 が通れば、移行は「いつでも止められる作業」になる。

## 6. 未解決

- 重ねた状態を**いつ畳むか**の判断は、まだ型になっていない。gonin では画像が1枚だったので
  即日畳めたが、旧が大量にある場合は「旧が空になったこと」を検査で保証しないと畳めない
- フォールバックは**旧が生きている間だけ正しい**。旧を消したあともコードに残ると、
  「無い」を隠す経路になる（CN-016 の裏返し）。畳むときにフォールバックも消す必要があるが、
  gonin では `public/img/` を空にしただけでコードは残してある＝これは意図的な残置か、
  消し忘れかを区別する記録が要る
