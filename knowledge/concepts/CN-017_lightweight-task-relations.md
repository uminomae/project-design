## なぜこのノートがあるか

家庭やごく小さなチームの工程管理に、プロジェクト管理ツールを入れると続かない。
理由は機能不足ではなく**属性が多すぎる**ことにある——工数、進捗率、開始/終了日、優先度の数値、
担当の役割分類。**入力する人が二人しかいない場では、埋まらない欄が場を殺す。**

futari で実際に運用に必要だったのは **3属性だけ**だった。

| 属性 | 値 | 何のためか |
|---|---|---|
| **担当（作業主体）** | 夫 / 妻 / 共通 | 「自分が今日やれるか」を判断する |
| **入れ子（親子）** | 親に子の表・子に `親: #N` | 大きな項目の中を一つずつ見る |
| **順序（F-S）** | 先行 / 後続 | **待ちがあるか**を判断する |

**そしてこの3つは、label と本文の記法だけで表せた。**閲覧 UI は静的 HTML で足りる。
ガントも依存グラフのレンダリングも要らなかった（**日付が無いから**）。

---

## 1. 担当を排他にしない — 第3の値「共通」がフィルタを包含にする

素朴には担当は排他分割になる（夫 か 妻）。**これだと「ふたりでやること」の行き場が無い。**
`共通` を第3の値として足すと、絞り込みが**集合の包含**になる:

```
夫 を選ぶ   → 夫 ∪ 共通
妻 を選ぶ   → 妻 ∪ 共通
共通 を選ぶ → 共通のみ
```

**絞り込みの目的は「自分に関係あるものを見る」ことであって、担当者で分類することではない。**
だから正しい演算は分割ではなく包含になる。RACI のような多役割（責任者・実行者・相談先・報告先）は
要らなかった——**1軸3値で足りた。**

### 粒度の発見: 担当は Issue 単位では表せない

「妻の GitHub アカウントを取得する」の中身は
**妻が作る → 夫が招待する → 妻が承諾する** と交代する。
Issue に1つだけ担当を持たせると、この交代が消える。
**⇒ 担当は工程の1行ごとに持たせ、Issue 単位の担当は「その中で主にやる人」の要約として置く。**
要約（絞り込み用）と実体（1行ごと）を分けると、両方成立する。

## 2. F-S を書く価値は「順序の指定」ではなく「並行可能性の解放」

先行/後続を書き始めて分かったのは、**書きたかったのは待ちの指定ではなく「これは待たなくていい」の
明示**だったということ。#12（GitHub アカウント）と #13（Claude プラン）は互いに独立で、
**同時に進めてよい**。これを書くまでは、上から順にやるものだと思われていた。

> **依存の記録は制約の追加に見えて、実際には待ちの解除として効く。**

だから記法には「先行: **なし（いつでも始められる）**」を必ず書く。空欄にしない。
**「不明」と「無い」の区別**という点で CN-016 と同じ型である。

---

## 3. 非技術者が読む依存図の書き方

読み手（妻）は用語を持たない。**先行・後続・クリティカルパス・マイルストーンを出さない。**

- 縦のレーン＋矢印、矢印のラベルは「**終わってから**」
- 並行は「**＋ 同時に進めてOK**」
- レーンは**目的で割る**（「見る側」「書く側」）。役割や工程名で割らない
- 最後に**合流**のレーンを1つ（「①と②の両方が終わってから」）

2レーン＋合流で、5〜10ステップの導入手順は伝わった。**ガントは日付が無いと描けないし、
日付が無いのが普通**なので、そもそも要らない。

---

## 4. 入れ子は2段で止まる

親に子の表、子に「親: #N」。それ以上の階層を作らない。
**3段目が要ると感じたら、それは親の粒度が大きすぎる兆候**として扱う。

閲覧側では、親カードの中に子のリンクを並べ、**子はそれぞれ独立したページを持つ**。
「一覧の中で開閉する」より「一つずつ別ページで見る」方が、スマホでは読みやすかった。

---

## 5. 判定テスト

項目を1つ見せて:

> **「自分が今日それをやれるか」が分かるか。**

分かるには3つが要る——**誰が**（担当）・**どこに属すか**（入れ子）・**待ちがあるか**（F-S）。
どれか1つでも欠けると、読んだ人は結局本人に聞く。**聞かれた時点で工程管理は機能していない。**

## 6. 未解決

- **二重管理**: 正本（GitHub Issue）と閲覧用（HTML）を手で同期している。乖離しうる。
  CN-013 に従うなら「Issue に存在する open な項目は、閲覧ページに必ず対応が1つある」という
  **不変条件の検査**にできるはずだが未実装。
- **`共通` の劣化**: 迷ったら共通にしておく誘惑がある。共通が過半を超えると絞り込みが効かなくなる。
  閾値も検知も未設計。
- **温度感と F-S の衝突**: 「したい（wish）だが先行なし＝今すぐ着手できる」と
  「必須だが待ちがある」の並べ方が決まっていない。優先度順ソートは前者を沈める。
  **着手可能性でのソート**（＝先行が全て閉じている項目を上げる）が要るかもしれない。
